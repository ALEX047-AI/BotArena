## 1. Назначение системы

**BotArena** — настольная программная среда для моделирования соревнований автономных программируемых агентов на двумерной клеточной арене. Каждый бот получает структурированное наблюдение об игровом состоянии и возвращает одно действие. Игровой движок проверяет действие, изменяет состояние и фиксирует результат.

В первой версии BotArena представляет собой **симулятор алгоритмов**, а не систему машинного обучения. Случайная стратегия, жадный поиск и A* — алгоритмические методы. Называть их нейросетями или обученными моделями без соответствующей реализации неправильно.

Система предназначена для трёх сценариев: обучения Python на реальном программном продукте, воспроизводимого сравнения стратегий и публичной демонстрации на конференции. Для первой версии выбран локальный режим без дополнительных аппаратных устройств и платных внешних API.

**Статус документа:** проектная спецификация версии 0.1 от 19.11.2026. Она определяет требования, но не подтверждает наличие готового кода, работающего интерфейса или результатов испытаний.



## 2. Проблема, цель, задачи и исследовательская гипотеза

При изучении программирования ученик часто решает отдельные упражнения без наблюдаемой связи между алгоритмом и его практическим поведением. BotArena позволяет наблюдать работу одного и того же правила управления в разных условиях, сопоставлять варианты и обнаруживать ошибки в собственных решениях.

**Цель разработки:** создать воспроизводимую 2D-среду на Python, где два автономных бота соревнуются за ресурсы по единым правилам, а алгоритмы управления поддаются тестированию и сравнительному анализу.

Задачи: определить правила матча; реализовать независимый от графики движок; разработать интерфейс бота; создать эталонные стратегии Random, Greedy и A*; реализовать Pygame-визуализацию; протоколировать матчи; подготовить тесты и методику эксперимента.

**Исследовательский вопрос:** как метод выбора действия влияет на эффективность сбора ресурсов при изменении плотности препятствий?

**Проверяемая гипотеза:** при наличии препятствий стратегия на основе A* будет в среднем собирать больше ресурсов, чем жадная стратегия, ориентирующаяся только на расстояние Манхэттена. Это предположение; результат необходимо устанавливать по измерениям, а не по названию алгоритма.

**Образовательный результат:** Роман Наумов осваивает базовые и прикладные элементы Python через самостоятельные фрагменты проекта и объясняет принятые решения. Оценка освоения подтверждается выполненными задачами, а не наличием сгенерированного исходного кода.

## 4. Роли пользователей и основные сценарии

**Исследователь** выбирает карту или начальное зерно генератора, назначает стратегию каждому боту, запускает матч, наблюдает за ходами, сохраняет отчёт и сравнивает несколько прогонов.

**Ученик-разработчик** изменяет доверенный локальный модуль стратегии, запускает тесты, сопоставляет собственный алгоритм с эталонным и объясняет почему изменился результат.

**Зритель на конференции** видит поле, положение двух ботов, собранные ресурсы, текущий раунд, итоговые очки и краткий вывод об эксперименте. Для демонстрации не требуется интернет или доступ к внешнему сервису.

Базовая последовательность: подготовка конфигурации → проверка карты → создание начального состояния → передача наблюдения первому активному боту → валидация действия → изменение состояния → логирование события → следующий бот → завершение раунда → итог матча → экспорт.



## 5. Правила игрового процесса v0.1

| Параметр | Проектное значение |
|---|---|
| Размер поля | 12 столбцов × 12 строк |
| Количество ботов | 2 (`A`, `B`) |
| Статические ресурсы | 10 штук; каждый приносит 1 очко |
| Длительность | Не более 100 раундов |
| Начальные очки | 0 у каждого |
| Допустимые действия | `UP`, `DOWN`, `LEFT`, `RIGHT`, `WAIT` |
| Перемещение | На одну клетку по вертикали или горизонтали |
| Сбор ресурса | Автоматически при входе на клетку с ресурсом |
| Ограничения | Нельзя выйти за границу, пройти стену или занять клетку другого бота |
| Конец матча | Собраны все ресурсы или прошёл 100-й раунд |
| Победа | Больше очков; при равенстве — ничья |

**Раунд** — возможность каждого бота выбрать ровно одно действие. Для MVP используется последовательное разрешение действий: в чётных раундах первым действует A, в нечётных — B. Второй бот получает обновлённое состояние. Это не одновременная механика; порядок хода записывается в журнал и учитывается при анализе. В исследованиях стороны и порядок стартовых условий меняются местами.

**Недопустимое действие** (столкновение, неизвестная команда, неправильный тип) не изменяет позицию бота, фиксируется как `INVALID_ACTION` и тратит текущий ход. Отсутствие ресурса под ботом не даёт очков. Команда `WAIT` допустима и также расходует ход. При одинаковых координатах на одном поле всегда может находиться не более одного бота.

Начальные позиции двух ботов различаются; обе клетки свободны. На них нет ресурса. Стены и ресурсы после начала матча неподвижны. Респавна ресурсов в MVP нет. Случайность при построении карты и в Random-стратегии управляется независимыми фиксируемыми зернами.

Правила относятся к предлагаемой реализации v0.1 и могут изменяться только через запись нового решения и обновление тестов, чтобы результаты старых экспериментов оставались интерпретируемыми.



## 6. Генерация и проверка карты

Координаты задаются целочисленной парой `(x, y)` с началом `(0, 0)` в левом верхнем углу; x растёт вправо, y — вниз. Допустимые значения — от 0 до 11 включительно. Стена не может совпадать с ресурсом или стартовой точкой.

В первой версии предлагается генератор с параметрами `map_seed`, `obstacle_density`, `resource_count=10`. Для исследования используются три уровня плотности препятствий: **10%, 20% и 30%** от 144 клеток. Фактическое число стен сохраняется в результате, поскольку округление долей даёт разные целые количества.

Генератор сначала резервирует две стартовые клетки, затем формирует стены и проверяет доступность карты. Для корректного сравнения каждый ресурс должен быть достижим из обеих начальных позиций по свободным клеткам в статической карте. Если условие не выполняется, генератор повторяет построение в рамках фиксированной воспроизводимой процедуры или отклоняет конфигурацию с понятной диагностикой. Карты и ресурсы должны сохраняться вместе с идентификатором или контрольной суммой.

Тестовые карты должны содержать также искусственные случаи: узкие коридоры, тупики, пустое поле, недостижимая цель и блокировка допустимого хода. Недостижимые ресурсы не должны попадать в основную исследовательскую выборку, но нужны для модульных тестов корректной обработки ошибок.



## 7. Контракт программируемого бота

Интерфейс разделяет **наблюдение** (`Observation`) и **действие** (`Action`). Контроллер получает только доступные по правилам данные и возвращает одну из пяти команд. Непосредственно изменять объекты игрового состояния контроллер не вправе.

Планируемое логическое описание вызова:

```python
# Иллюстрация контракта; не подтверждение существования модуля.
def decide(observation: Observation) -> Action:
    ...
```

Минимальное наблюдение содержит `round_index`, `max_rounds`, `arena_width`, `arena_height`, координаты стен и ресурсов, координаты своего и второго бота, очки обоих участников, идентификатор активного бота. Для MVP действует **полная наблюдаемость**: положение ресурсов и соперника видно целиком. Концепция ограниченного радиуса обзора отложена.

Планируемый пример структуры данных:

```json
{
  "round_index": 12,
  "max_rounds": 100,
  "self_id": "A",
  "self_position": [2, 3],
  "opponent_position": [8, 7],
  "scores": {"A": 3, "B": 2},
  "arena_size": [12, 12],
  "walls": [[4, 4], [4, 5]],
  "resources": [[1, 8], [9, 2]]
}
```

Это **проектный пример**, а не зафиксированный формат готового файла. Python-API должен использовать типизированные внутренние модели и передавать боту копию или неизменяемое представление наблюдения.

Ошибки стратегии не должны повреждать состояние матча: движок перехватывает исключение, регистрирует тип ошибки и применяет оговорённую политику `WAIT` с записью `BOT_ERROR`. Время исполнения контроллера в MVP учитывается диагностически; полноценные квоты CPU/памяти относятся к следующему этапу. В первой версии подключаются только доверенные локальные модули, а не произвольный код от сторонних пользователей.



## 8. Эталонные стратегии

**Random.** Равновероятно выбирает допустимое действие перемещения среди возможных направлений; если движения нет, возвращает `WAIT`. Использует выделенный генератор случайных чисел с указанным seed. Это контрольный базовый алгоритм.

**Greedy.** Ищет ближайший ресурс по расстоянию Манхэттена и выбирает соседний допустимый шаг, уменьшающий это расстояние. При равенстве применяется устойчивый порядок направлений, прописанный в реализации и журнале. Жадная стратегия не исследует всю карту: она может застревать в локально неудачных решениях из-за стены или тупика.

**A*.** Рассматривает свободные клетки как граф с рёбрами между соседними клетками и весом 1; для выбора ресурса строит кратчайший путь алгоритмом A* с эвристикой Манхэттена, допустимой на такой сетке. При нескольких ресурсах выбирает достижимую цель с минимальной длиной найденного пути. Занятая соперником клетка считается временно недоступной; при изменении расположения противника маршрут пересчитывается. Если доступных ресурсов нет, возвращает `WAIT`.

Для каждой стратегии фиксируются версия алгоритма и параметры. Корректность A* проверяется относительно BFS на небольших эталонных картах. Условия сравнения не должны давать одному контроллеру дополнительную информацию или больше игровых действий.



## 9. Архитектура и границы компонентов

| Компонент | Зона ответственности | Не должен делать |
|---|---|---|
| `core` | Правила игры, раунды, победитель, валидация команд | Рисовать интерфейс |
| `arena` | Клетки, стены, ресурсы, проверка карты | Решать за бота |
| `bots` | Контракт наблюдения и стратегии Random/Greedy/A* | Изменять `GameState` напрямую |
| `ui` | Pygame-визуализация и кнопки управления | Вычислять победителя |
| `tournament` | Серии матчей, перестановки сторон и агрегированные показатели | Менять правила отдельного матча |
| `storage` | JSON/CSV, метаданные и загрузка протоколов | Скрыто менять игровой результат |

Базовая структура **предлагаемая**, а не уже созданная:

```text
src/botarena/
  core/           # состояние и выполнение ходов
  arena/          # карта и генерация
  bots/           # интерфейс и стратегии
  ui/             # Pygame
  tournament/     # серии матчей и статистика
  storage/        # сохранение результатов
tests/
  unit/
  integration/
  fixtures/
docs/
research/
```

Движок должен работать **без Pygame**: это необходимо для автоматизированных тестов, массовых запусков и воспроизводимых исследований. UI подписывается на события состояния или считывает снимок после выполнения игрового шага. Графическая частота кадров не определяет число игровых ходов.

Основной принцип зависимостей: `ui → core`, `tournament → core`, `core → arena` и контракт `bots`, `storage` работает с результатами. Циклических импортов и обратной зависимости `core → ui` быть не должно.



## 10. Модели данных, события и воспроизводимость

| Сущность | Существенные поля |
|---|---|
| `ArenaConfig` | width, height, map_seed, obstacle_density, resource_count |
| `ArenaState` | walls, remaining_resources, starts, map_id |
| `BotState` | id, position, score, strategy_id |
| `GameState` | arena, bots, round_index, turn_order, status |
| `Observation` | read-only state visible to a bot |
| `GameEvent` | round, actor, requested_action, applied_action, position_before/after, outcome |
| `MatchResult` | winner, final_scores, rounds_played, map_id, seed, versions, errors |
| `ExperimentRun` | dataset_id, strategy_pair, side_assignment, config, result_path |

Журнал событий фиксирует входную конфигурацию, версии правил и алгоритмов, действия, начисления очков, ошибки контроллеров и причину завершения матча. Для последующего воспроизведения необходимы карта/seed, порядок ходов, версии стратегий и их собственные случайные зерна.

**Формат результатов:** JSON для полного отдельного матча и CSV для сводной таблицы по серии. Поля, сериализация и точные имена файлов уточняются при разработке, после чего фиксируются в схеме с версией (`schema_version`). Протокол не содержит ключей доступа и пользовательских секретов.

Одинаковый `map_seed` гарантирует сравнимую карту только при неизменной версии генератора и алгоритма случайных чисел. Поэтому для серьёзного эксперимента дополнительно сохраняется фактическое поле и его контрольная сумма.



## 11. Графический интерфейс

Целевой интерфейс Pygame содержит: клеточное поле 12×12; стены; ресурсы; различимые обозначения двух ботов; счёт каждого; номер раунда; статус матча; название стратегии каждого участника; управляющие действия «Старт», «Пауза», «Шаг», «Перезапуск».

Рабочий экран должен отделять игровой мир от панели управления и статистики. Размер клетки масштабируется в пределах окна. Цвет не служит единственным средством различения ботов: кроме цвета используются буквы A и B или отдельные формы маркеров.

В режиме пошагового просмотра один запрос «Шаг» может выполнять ход следующего бота либо один полный раунд; точный вариант нужно закрепить в GUI-тестах и надписях. Предпочтение для MVP — один полный раунд, чтобы пользователь видел действия обоих ботов.

Если Pygame недоступен, ядро и тесты по-прежнему должны запускаться в режиме без графики. Приложение не должно требовать подключения к интернету для обычного локального матча.

## 13. Методика исследовательских экспериментов

### Дизайн сравнения

Для основного исследования предлагаются три пары стратегий: `Random–Greedy`, `Random–A*`, `Greedy–A*`. Для каждого из трёх уровней плотности препятствий (10%, 20%, 30%) подготавливается **30 фиксированных seed карты**. На каждой карте пара запускается дважды с перестановкой сторон A/B. Полный план: `3 пары × 3 уровня × 30 карт × 2 перестановки = 540 матчей`.

Это **план выборки**, а не утверждение о проведённых 540 матчах. Если сроки не позволят, публикуется фактическое количество запусков без подмены плана результатом; сокращение выборки отражается как ограничение исследования.

### Измерения

Для каждой стратегии и уровня сложности фиксируются: среднее число очков, число побед/ничьих/поражений, доля побед (отдельно доля ничьих), число недопустимых действий, среднее число раундов, при необходимости — время вычисления действий. Число наблюдений и разброс значений указываются в отчёте.

Из-за парного дизайна результаты сравниваются на одинаковых картах. Обычная средняя победа без указания состава карт и перестановки сторон недостаточна. Случайный контроллер использует фиксируемые семена, не разделяя глобальный RNG с генератором арены.

### Интерпретация

Гипотеза может подтвердиться, частично подтвердиться или не подтвердиться. Нельзя утверждать, что A* всегда сильнее Greedy: результат зависит от правил, числа ресурсов, поведения противника и используемой стратегии выбора цели. Научная новизна формулируется осторожно — как постановка и проведение проверяемого сравнительного эксперимента в собственной среде, без заявлений об изобретении новых алгоритмов.

Результат исследования сопровождается ссылкой на версию кода, параметры запуска, набор карт/seed, исходные CSV/JSON и описание выявленных ограничений.

## 15. Надёжность, безопасность и ограничения

**Изоляция:** до реализации отдельной безопасной среды исполнения BotArena загружает только доверенные локальные Python-модули проекта. Публичное API написания стратегий не означает, что можно безопасно выполнять любой присланный `.py`-файл. Подключение внешних пользовательских ботов потребует изоляции процессов, ограничений ресурсов, файлового доступа и проверки угроз.

**Целостность:** стратегия не изменяет игровое состояние в обход движка; любые полученные команды валидируются. При сбое контроллера журнал фиксирует ошибку, а матч не должен повреждать исходную карту.

**Воспроизводимость:** версии правил и алгоритмов, seed, карта и входные параметры фиксируются. Порядок действий определяется документированным циклом, не частотой обновления графики.

**Ограничения модели:** клеточная карта упрощает реальную робототехнику; препятствия статичны; датчики идеализированы; полноценной физики движения нет; агенты в MVP не обучаются на опыте. Перенос выводов на реальных роботов без дополнительных исследований не допускается.

**Конфиденциальность:** API-ключи, токены, `.env`, личные сведения и внутренние рабочие заметки не помещаются в публичный репозиторий; закрытый репозиторий также не считается безопасным местом для секретов.

## 20. Открытые вопросы и порядок изменения спецификации

Каждое изменение правил фиксируется в журнале решений, обновляет спецификацию и связанные тесты. Отчёты экспериментов всегда привязаны к версии правил, при которой были получены.
